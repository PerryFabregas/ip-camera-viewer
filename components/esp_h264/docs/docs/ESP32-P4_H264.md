# H.264 sur ESP32‑P4 (`esp_h264`)

Documentation du composant `esp_h264` tel qu'il est intégré dans ce dépôt
(`ip-camera-viewer`). Elle décrit l'accélérateur matériel H.264 de l'ESP32‑P4,
les chemins logiciels (software) de repli, l'API C exposée, ainsi que la
configuration et l'usage concret par le composant ESPHome `ip_camera_viewer`.

> Source : composant `esp_h264` (portage du composant Espressif `esp-video`),
> en‑têtes `interface/include/`, HAL `hw/hal/esp32p4/`, libs `sw/libs/esp32p4/`.

---

## 1. Vue d'ensemble

L'ESP32‑P4 dispose d'un **encodeur H.264 matériel** (bloc dédié + DMA). Le
composant fournit trois chemins :

| Chemin | Rôle | Cible | Implémentation |
| ------ | ---- | ----- | -------------- |
| **Encodeur matériel (HW)** | YUV → H.264 | ESP32‑P4 uniquement | bloc H.264 + DMA (`hw/`) |
| **Encodeur logiciel (SW)** | YUV → H.264 | P4 / S3 | openh264 (`sw/libs/.../libopenh264.a`) |
| **Décodeur logiciel (SW)** | H.264 → YUV | P4 / S3 | tinyH264 / openh264 (`sw/libs/.../libtinyh264.a`, `libopenh264.a`) |

Il **n'existe pas de décodeur matériel** : l'ESP32‑P4 accélère l'**encodage**,
le décodage reste logiciel. C'est précisément ce que fait le composant
`ip_camera_viewer` (réception RTSP/H.264 → décodage logiciel → YUV → affichage).

Cibles supportées par les `test_apps` : **ESP32‑P4** et **ESP32‑S3**
(`test_apps/README.md`). L'encodeur **matériel** n'existe que sur P4.

## 2. Capacités de l'encodeur matériel ESP32‑P4

Référence : `interface/include/esp_h264_types.h` et `hw/hal/esp32p4/h264_config.h`.

### Résolution

| | Encodeur logiciel | **Encodeur matériel (P4)** |
| --- | --- | --- |
| Largeur max | illimitée | **1920** |
| Largeur min | 16 | **80** |
| Hauteur max | illimitée | **2032** |
| Hauteur min | 16 | **80** |

> Largeur et hauteur doivent être **multiples de 16** (taille macrobloc).
> Pour arrondir : `width = ((width + 15) >> 4) << 4;` (idem hauteur).

### Format de pixel en entrée

L'entrée non encodée est décrite par `esp_h264_raw_format_t` :

| Format | Encodeur SW | **Encodeur HW (P4)** | Décodeur SW |
| ------ | ----------- | -------------------- | ----------- |
| `ESP_H264_RAW_FMT_YUYV` (YUV422 packed) | ✅ | ❌ | ❌ |
| `ESP_H264_RAW_FMT_I420` (YUV420 planar) | ✅ | ❌ | ✅ |
| `ESP_H264_RAW_FMT_O_UYY_E_VYY` (YUV420 packed) | ❌ | ✅ | ❌ |

> ⚠️ Point clé : l'encodeur **matériel** P4 n'accepte **que** le format
> `ESP_H264_RAW_FMT_O_UYY_E_VYY` (lignes impaires `u y y …`, lignes paires
> `v y y …`). Une conversion de format est donc nécessaire si la caméra fournit
> du I420/YUYV.

### Profil / QP / contrôle de débit

- **QP** (paramètre de quantification) : plage `[0, 51]` (`ESP_H264_QP_MAX = 51`).
  QP faible = meilleure qualité, moindre compression.
- **Contrôle de débit** (`esp_h264_enc_rc_t`) : `bitrate` cible, `qp_min`,
  `qp_max`. Recommandation : `bitrate ≈ width * height * pixel / taux_compression`
  (H.264 atteint couramment >100× de compression).
- **GOP** (`gop`) : période des images Intra ; typiquement réglé à la valeur du
  FPS (25 ou 30). Plage 1–255.
- **FPS** (`fps`) : 1–255.

### Fonctionnalités matérielles avancées (`esp_h264_enc_param_hw.h`)

- **ROI (Region Of Interest)** — jusqu'à **8 régions** (`reg_idx < 8`). Modes :
  - `ESP_H264_ROI_MODE_FIX_QP` : QP fixe par région (`qp` ∈ [0, 51]).
  - `ESP_H264_ROI_MODE_DELTA_QP` : delta QP ajouté au QP de slice (`qp` ∈ [‑51, 51]).
  - `ESP_H264_ROI_MODE_DISABLE`.

  Permet d'allouer plus de débit aux zones importantes (meilleure qualité) et
  moins aux zones secondaires → économie de bande passante / stockage.
- **Motion Vectors (MV)** — extraction des vecteurs de mouvement par macrobloc
  16×16 (`ESP_H264_MVM_MODE_P16X16`, `MINV`, `MAXV`) et formats de sortie
  (`ALL`, `PART`). Utile pour détection de mouvement assistée par l'encodeur.

### Constantes matérielles (`hw/hal/esp32p4/h264_config.h`)

| Macro | Valeur par défaut | Signification |
| ----- | ----------------- | ------------- |
| `CONFIG_H264_MAX_CHANNELS` | `2` | nombre max de canaux (→ encodage **dual stream**) |
| `CONFIG_H264_DMA_BUFFER_ALIGN` | `64` | alignement des buffers DMA (octets) |
| `CONFIG_H264_INTR_PRIORITY` | `1` | priorité d'interruption |
| `CHIP_SUPPORT_MIN_REV` | `200` | révision puce minimale (v2.0) |

> Le bloc matériel existe en plusieurs révisions de silicium : voir
> `hw/soc/esp32p4/hw_ver1/` et `hw/soc/esp32p4/hw_ver3/` (registres différents).

## 3. API C

Toutes les fonctions renvoient `esp_h264_err_t` (`esp_h264_types.h`) :
`ESP_H264_ERR_OK (0)`, `ERR_FAIL (-1)`, `ERR_ARG (-2)`, `ERR_MEM (-3)`,
`ERR_UNSUPPORTED (-5)`, `ERR_TIMEOUT (-6)`, `ERR_OVERFLOW (-7)`.

### 3.1 Encodeur matériel — flux simple (single stream)

En‑tête : `hw/include/esp_h264_enc_single_hw.h`.

```c
#include "esp_h264_enc_single_hw.h"

esp_h264_enc_cfg_hw_t cfg = {
    .pic_type = ESP_H264_RAW_FMT_O_UYY_E_VYY,   // seul format accepté par le HW
    .gop      = 30,
    .fps      = 30,
    .res      = { .width = 1280, .height = 720 },
    .rc       = { .bitrate = 1280 * 720 * 2, .qp_min = 25, .qp_max = 40 },
};

esp_h264_enc_handle_t enc = NULL;
ESP_ERROR_CHECK( esp_h264_enc_hw_new(&cfg, &enc) );   // crée l'instance HW
ESP_ERROR_CHECK( esp_h264_enc_open(enc) );            // ouvre l'encodeur

// Boucle d'encodage
esp_h264_enc_in_frame_t  in  = { .raw_data = { .buffer = yuv, .len = yuv_len }, .pts = pts };
esp_h264_enc_out_frame_t out = { .raw_data = { .buffer = bitstream, .len = bs_cap } };
esp_h264_err_t r = esp_h264_enc_process(enc, &in, &out);
// out.frame_type (IDR/I/P), out.length = octets H.264 produits, out.dts/out.pts

esp_h264_enc_close(enc);
esp_h264_enc_del(enc);
```

Réglage des paramètres à chaud (via le handle de paramètres) :

```c
esp_h264_enc_param_hw_handle_t param = NULL;
esp_h264_enc_hw_get_param_hd(enc, &param);

esp_h264_enc_set_bitrate(&param->base, 2 * 1000 * 1000);
esp_h264_enc_set_fps(&param->base, 25);
esp_h264_enc_set_gop(&param->base, 25);

// ROI
esp_h264_enc_hw_cfg_roi(param, (esp_h264_enc_roi_cfg_t){ .roi_mode = ESP_H264_ROI_MODE_DELTA_QP, .none_roi_delta_qp = 10 });
esp_h264_enc_hw_set_roi_region(param, (esp_h264_enc_roi_reg_t){ .x=0,.y=0,.len_x=4,.len_y=4,.qp=-10,.reg_idx=0 });
```

Notes importantes (`esp_h264_enc_single.h`) :
- L'encodage matériel renvoie `ESP_H264_ERR_TIMEOUT` si `out.raw_data.len` est
  trop petit pour contenir la trame encodée.
- Le buffer d'entrée doit être alloué aligné : `esp_h264_aligned_calloc(16, …, MALLOC_CAP_DEFAULT)`.
- Pour une image IDR, SPS et PPS sont automatiquement ajoutés au NAL.

### 3.2 Encodeur matériel — flux double (dual stream)

En‑tête : `hw/include/esp_h264_enc_dual_hw.h`. Permet d'encoder **deux flux
simultanément** (p. ex. haute + basse résolution) avec le même GOP.

```c
esp_h264_enc_cfg_dual_hw_t cfg = { .cfg0 = cfg_hd, .cfg1 = cfg_sd };
esp_h264_enc_dual_handle_t enc = NULL;
esp_h264_enc_dual_hw_new(&cfg, &enc);
esp_h264_enc_dual_hw_get_param_hd0(enc, &param0);
esp_h264_enc_dual_hw_get_param_hd1(enc, &param1);
```

> Les deux flux doivent avoir le **même GOP** ; l'encodeur prend la moyenne des
> deux GOP, appliquée à l'image Intra.

### 3.3 Décodeur logiciel

En‑têtes : `interface/include/esp_h264_dec.h`, `sw/include/esp_h264_dec_sw.h`.

```c
esp_h264_dec_cfg_sw_t dec_cfg = {};
dec_cfg.pic_type    = ESP_H264_RAW_FMT_I420;
dec_cfg.profile_idc = ESP_H264_PROFILE_AUTO;   // auto-détection depuis le flux

esp_h264_dec_handle_t dec = NULL;
esp_h264_dec_sw_new(&dec_cfg, &dec);
esp_h264_dec_open(dec);
// esp_h264_dec_process(dec, &in, &out) en boucle (gérer in.consume)
```

Profils H.264 (`esp_h264_profile_idc_t`) : `BASELINE (66)`, `MAIN (77)`,
`EXTENDED (88)`, `HIGH (100)`, `HIGH10 (110)`, `HIGH422 (122)`, `HIGH444 (244)`,
`AUTO (0)`.

> ⚠️ Limite décodeur : **tinyH264** ne décode que le profil **Constrained
> Baseline**. **openh264** (utilisé ici, `profile_idc = AUTO`) gère
> Baseline / Main / High. Si la source émet du Main/High avec tinyH264, le flux
> ne sera pas décodé → il faut transcoder en Baseline (go2rtc/ffmpeg).

## 4. Intégration ESPHome

### 4.1 Le composant `esp_h264` (`__init__.py`)

C'est un composant **interne** (bibliothèque) — son `CONFIG_SCHEMA` est
`cv.invalid(...)`, il ne se déclare donc pas directement dans le YAML. Il est
tiré comme dépendance par `esp_video` / `ip_camera_viewer`.

Il ajoute les chemins d'include (`interface/include`, `port/include`,
`hw/include`, `sw/include`, `port/inc`) et active le **décodage H.264 bi‑cœur**
sur ESP32‑P4 (gain de perfs annoncé 30–50 %) :

```python
cg.add_build_flag("-DCONFIG_ESP_H264_DUAL_TASK=1")
cg.add_build_flag("-DCONFIG_ESP_H264_DUAL_TASK_CORE=1")
cg.add_build_flag("-DCONFIG_ESP_H264_DUAL_TASK_PRIORITY=17")
```

> Les sources C sont compilées par le script `esp_video_build.py` (PlatformIO),
> pas via `cg.add_library()`, pour éviter la double compilation.

### 4.2 Usage par `ip_camera_viewer`

Le composant `ip_camera_viewer` (`components/ip_camera_viewer/ip_camera_viewer.cpp`)
implémente un **client RTSP/H.264** :

- Réception RTP/RTSP, réassemblage des NAL units dans `h264_buffer_`
  (`MAX_H264_SIZE = 256 KiB`, alloué en PSRAM : `MALLOC_CAP_SPIRAM`).
- Mise en cache de **SPS/PPS** et ré‑injection devant les trames IDR.
- Décodage logiciel via `esp_h264_dec_sw_new` (config `I420`, profil `AUTO`).
- Détection du profil du flux : avertissement explicite si le flux n'est pas
  Baseline et que seul tinyH264 est disponible.
- Adaptation réseau du débit d'images : 5 FPS (réseau faible) / 10 FPS (moyen) /
  15 FPS (élevé).

## 5. Configuration recommandée (sdkconfig ESP32‑P4)

Extrait de `test_apps/sdkconfig.defaults.esp32p4` :

```ini
# CPU & cache
CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ=360
CONFIG_CACHE_L2_CACHE_128KB=y
CONFIG_CACHE_L2_CACHE_LINE_SIZE=128

# PSRAM (obligatoire pour les buffers vidéo)
CONFIG_SPIRAM=y
CONFIG_SPIRAM_MODE_HEX=y
CONFIG_SPIRAM_SPEED=200
CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y

# H.264
CONFIG_ESP_H264_DECODER_IRAM=y        # décodeur en IRAM (perf)
CONFIG_IDF_EXPERIMENTAL_FEATURES=y

# Optimisation
CONFIG_COMPILER_OPTIMIZATION_PERF=y
```

Pré‑requis IDF : **ESP‑IDF ≥ 5.0** (`idf_component`).

## 6. Pièges fréquents (récapitulatif)

1. **Format d'entrée HW** : l'encodeur matériel n'accepte **que**
   `O_UYY_E_VYY` — prévoir une conversion depuis I420/YUYV.
2. **Multiples de 16** : largeur et hauteur doivent être arrondies au macrobloc.
3. **Buffer de sortie trop petit** → `ESP_H264_ERR_TIMEOUT` (HW) ou
   `ESP_H264_ERR_OVERFLOW` ; dimensionner `out.raw_data.len`.
4. **Alignement DMA** : entrées allouées via `esp_h264_aligned_calloc` (align 16),
   buffers DMA alignés sur 64 octets.
5. **Décodage** : pas d'accélération matérielle → openh264/tinyH264 logiciel ;
   attention au profil (Baseline pour tinyH264).
6. **PSRAM requise** pour les buffers H.264/YUV (résolutions élevées).
7. **Bornes HW** : 80×80 min, 1920×2032 max — au‑delà, utiliser l'encodeur SW.

## 7. Tests

Le composant fournit des `test_apps` (cibles **ESP32‑P4** / **ESP32‑S3**) :

- `main/esp_h264_hw_enc_test.c` — encodeur **matériel** (P4).
- `main/esp_h264_sw_enc_test.c` — encodeur **logiciel**.
- `main/esp_h264_sw_dec_test.c` — décodeur **logiciel**.
- `pytest_h264.py` + `.build-test-rules.yml` — orchestration pytest‑embedded.

Lancement type (depuis `test_apps/`) :

```bash
idf.py set-target esp32p4
idf.py build flash monitor
# ou via pytest-embedded : pytest pytest_h264.py --target esp32p4
```
